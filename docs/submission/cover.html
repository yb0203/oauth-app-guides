Our understanding

How OAuth apps, Composio and user connections fit together

OAuth lets a user grant an app limited, revocable access without sharing their password. But before any user can click "Allow", the developer needs an approved OAuth app at the provider.

1 · Provider OAuth app

The gate

The developer's client registration at Google, Xero or Shopify: client ID and secret, redirect URI, scopes, consent screen. Often needs the provider's approval.

→
2 · Composio auth config

The integration

Which OAuth app and scopes to use for a toolkit. Composio's own managed app (123 toolkits) or the developer's own (required for 211).

→
3 · Connected accounts

The users

One per end user, holding that user's tokens. One OAuth app serves thousands of them, so if layer 1 isn't approved, nobody can connect.

Scopes are the biggest lever

The same app can be easy or hard depending on the permissions requested. For Gmail, internal-only apps need no review, sending email is a sensitive scope (a review lasting days), and reading email is a restricted scope (review plus a paid yearly security assessment). A good guide shows what each permission costs.

Gatekeepers on both sides

Passing the provider's review isn't the end. Customers' own admins can still block an app: Microsoft tenants often need admin consent, GitHub organizations restrict OAuth apps by default, and Slack workspaces can require approved apps. Guides cover both sides.

The problem

Every user connection depends on an OAuth app someone has to get approved

When an AI agent connects to a user's Gmail, Xero or Shopify, it does so through a provider OAuth app: a client registration the developer creates at the provider.

Where developers get stuck

Composio supplies a managed app for 123 toolkits. For the other 211, and whenever a developer wants their own branding, rate limits or scopes, they must register their own app and often get it approved.

Setup can take five minutes (GitHub) or weeks with a paid security audit (reading Gmail). Sometimes only established companies are accepted (Spotify). Nobody can tell in advance which it'll be.

Why this isn't "ask a chatbot"

Asked from memory, a model was wrong on several of these points: Spotify's user cap, GitHub's token default, which tier each app falls in. Providers changed their rules several times in 2026, and their own docs sometimes contradict each other.

So the product is a research-and-verification process. The guide is its output.

Every guide answers four questions
How hard is it?One of four tiers: Instant, Verify to scale, Review required, or Partner only, with confidence.
How long will it take?Your hands-on hours and the provider's waiting time, shown separately.
What do I need?Accounts, limits, review requirements, customer-side gates and gotchas.
Who does what?Which steps the agent can do, and exactly where you have to take over.

Why an agent can't simply create the OAuth app: we tested it. On five providers, an agent with a real browser hit a sign-in page after one redirect every time. Everything past that (terms, Register, payment, review) needs a human. So the agent probes the console, does the research and drafts the materials (minimum scopes, justifications, consent-screen values), then hands off clearly.

Key decisions

Six choices that shaped the product

Each one came from something we tested or measured, not from assumptions.

A verification process, not a prompt

Answers from memory were wrong or stale, so checking against live docs is the product.

No pretend automation

All 5 consoles stopped at sign-in. The agent probes, researches and drafts, then hands off.

Code verifies, models write

Search, probing, quote checks, labels and tier rules are deterministic. Models extract claims and write, and their output is validated.

Bring-your-own first

Even for Composio-managed apps, guides cover registering your own app, and say when the managed one is enough.

Free models only

Runtime uses free OpenRouter models behind a server allow-list. Claude Code was used only to build and test.

Depth over breadth

5 varied apps done well, plus live generation for any app, instead of 100 shallow guides.

Performance and cost

  • ~66 seconds per guide on the default free model (8 runs, 51–96 s).
  • ~33,000 tokens per guide over about 7 model calls.
  • $0 actual spend; the same tokens on a paid model would cost about $0.03 per guide.
  • Most of the time goes to the model writing (about half) and reading pages.

Verification

  • ~75 research quotes re-checked independently; 1 citation fixed.
  • 247 live quote checks on the curated guides.
  • A quote-checker bug found and fixed: limits hidden in collapsed sections.
  • 420 backend tests, plus live-network tests.
Limitations

What doesn't work perfectly yet

Each limitation in plain words, what it means for you, and what softens it today.

LimitationWhat it means for youWhat helps today
Console forms are behind a loginWe can't see the real sign-up forms, so exact field names and logo rules aren't verified.Marked “check on first sign-in”. Everything else is checked against public docs.
Generated guide links can expireA link to a guide you just generated may stop working after the server restarts.The five curated guides are permanent. Use Export Markdown to keep a copy.
Some docs need a browser to loadDocs pages built with JavaScript can't be read on the live server, so those facts may show as Uncertain.They work when run locally with a browser installed.
Free models can miss numbersA generated guide may leave out a specific limit, such as Gmail's 100-user cap.Curated guides include them. A paid model is an option (about $0.03 a guide).
Difficulty can read stricter than it isIf any common path needs review, the tier says “Review required”, even when the basic path doesn't.The summary and the “Your situation” toggles explain the difference.

Progress can occasionally go quietTwice in testing, live updates stopped while the server carried on.The page now checks the run's status and loads the finished guide anyway.
Rules changeProviders changed their OAuth rules several times in 2026.Every guide shows its “last verified” date.

Where this could go next

Options we identified while building, roughly in order of value. Several are already partly designed or prototyped in the repo.

For developers

Inside Composio's dashboardShow the guide right where a developer creates a bring-your-own auth config: callback prefilled, scopes suggested, a redirect-mismatch checker.
Submission packOne-click download of the drafted privacy-policy outline, scope justifications, consent-screen values and a demo-video script for the provider's review.
Checklist and comparisonTrack setup progress in the shareable link, and compare two or three apps side by side before committing to one.

Better evidence

Signed-in human passCapture real console forms once, using test accounts (for example with Browser Use), to turn "check on first sign-in" into tested steps.
Continuous re-verificationRe-check every guide's quotes on a schedule, and flag guides whose source pages changed. Providers changed their rules several times in 2026.
Real wait-time dataLet developers report how long their review actually took, replacing anecdotal community estimates.
